This section documents the complete CI/CD pipeline implementation for the Chess Club Ranking System, covering the build, test, and deployment phases using Jenkins, Docker, and Kubernetes.

## Build Phase

### Tools and Frameworks

| Tool/Technology | Version | Purpose |
|----------------|---------|---------|
| Docker | 28.5.1 | Container image building |
| Node.js (Alpine) | 18 | Base image for application |
| Minikube Docker Daemon | 1.37.0 | Local Docker environment |
| npm | 10.8.2 | Dependency management |

### Configuration

**Dockerfile:**

```dockerfile
FROM node:18-alpine
WORKDIR /app

# Copy package files for dependency installation
COPY package.json package-lock.json ./

# Install production dependencies
# Skip scripts to avoid git hooks in container environment
RUN npm ci --omit=dev --ignore-scripts

# Copy application files
COPY . .

# Expose application port
EXPOSE 5000

# Health check for Kubernetes liveness probes
HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
  CMD node -e "require('http').get('http://localhost:5000', (r) => {process.exit(r.statusCode === 200 ? 0 : 1)})"

CMD ["node", "index.js"]
```

**Key Design Decisions:**
1. **Multi-layer caching**: Package files copied separately to leverage Docker layer caching
2. **Alpine Linux base**: Minimal image size (131MB vs 900MB+ for full Node.js image)
3. **Production-only dependencies**: Using `--omit=dev` reduces image size and attack surface
4. **Script skipping**: `--ignore-scripts` prevents husky git hooks from failing in containerized environment

**.dockerignore:**

The `.dockerignore` file excludes unnecessary files from the build context, reducing build time and image size:
- Development dependencies and tools
- Test files and coverage reports
- Git repository and CI/CD configurations
- Documentation and screenshots

## Deployment Phase

### Tools and Frameworks

| Tool/Technology | Version | Purpose |
|----------------|---------|---------|
| Kubernetes | 1.34.0 | Container orchestration |
| Minikube | 1.37.0 | Local Kubernetes cluster |
| kubectl | 1.34.1 | Kubernetes CLI |

### Configuration

**Kubernetes Deployment (`k8s/deployment.yaml`):**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: chess-ranking-deployment
spec:
  replicas: 2  # High availability with 2 pods

  selector:
    matchLabels:
      app: chess-ranking

  template:
    spec:
      containers:
      - name: chess-ranking-container
        image: chess-ranking:latest
        imagePullPolicy: Never  # Use local Minikube image

        ports:
        - containerPort: 5000

        # Resource limits prevent pod from consuming excessive resources
        resources:
          requests:
            memory: "128Mi"
            cpu: "100m"
          limits:
            memory: "256Mi"
            cpu: "500m"

        # Liveness probe - restart container if unhealthy
        livenessProbe:
          httpGet:
            path: /
            port: 5000
          initialDelaySeconds: 30
          periodSeconds: 10

        # Readiness probe - don't route traffic until ready
        readinessProbe:
          httpGet:
            path: /
            port: 5000
          initialDelaySeconds: 10
          periodSeconds: 5
```

**Kubernetes Service (`k8s/service.yaml`):**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: chess-ranking-service
spec:
  type: NodePort
  selector:
    app: chess-ranking
  ports:
  - port: 5000          # Internal cluster port
    targetPort: 5000    # Container port
    nodePort: 30080     # External access port
  sessionAffinity: ClientIP  # Sticky sessions
```

**Key Design Decisions:**

1. **Replica Count**: 2 replicas for high availability and zero-downtime deployments
2. **Resource Limits**: Prevent resource starvation in shared cluster
3. **Health Checks**:
   - Liveness probe ensures containers are restarted if unresponsive
   - Readiness probe prevents traffic to pods that aren't ready
4. **NodePort Service**: Allows external access for development/testing
5. **Session Affinity**: Ensures user sessions remain on same pod

## Challenges and Solutions

### Challenge 1: Husky Git Hooks Failing in Docker Build

**Problem:**
The npm install process triggered husky git hooks during Docker image build. Since git is not available in the Alpine Linux container, the build failed with error code 127.

**Error:**
```
npm error command failed
npm error command sh -c husky
sh: husky: not found
```

**Root Cause:**
The `prepare` script in package.json automatically runs husky to set up git hooks, which is unnecessary and problematic in containerized production environments.

**Solution:**
Modified the Dockerfile to skip npm scripts during dependency installation:

```dockerfile
# Before:
RUN npm ci --only=production

# After:
RUN npm ci --omit=dev --ignore-scripts
```

**Outcome:**
Build completed successfully in 8 seconds. Production dependencies installed without attempting to run git hooks.

**Learning:**
Container builds should exclude development tooling. The `--ignore-scripts` flag is essential when containerizing applications that use git hooks or other local development automation.

---

### Challenge 2: Docker and Minikube Environment Integration

**Problem:**
Jenkins needed to build Docker images that Kubernetes (Minikube) could access. By default, Jenkins uses the host's Docker daemon, but Minikube uses its own internal Docker daemon.

**Symptoms:**
- Images built by Jenkins not visible to Kubernetes
- Deployment fails with ImagePullBackOff error
- `imagePullPolicy: Always` attempts to pull from remote registry

**Solution:**
Configured Jenkins to use Minikube's Docker daemon:

```groovy
bat '''
    FOR /f "tokens=*" %%i IN ('minikube docker-env') DO %%i
    docker build -t chess-ranking:latest .
'''
```

And set Kubernetes to use local images:
```yaml
imagePullPolicy: Never
```

**Outcome:**
Images built by Jenkins are immediately available to Minikube for deployment.

**Learning:**
When using Minikube, always configure build tools to use the Minikube Docker environment to avoid image availability issues.

---

### Challenge 3: Windows Path Handling in Jenkins Pipeline

**Problem:**
Jenkins Pipeline scripts using `sh` (Unix shell) commands failed on Windows environment.

**Error:**
```
java.io.IOException: Cannot run program "sh"
```

**Solution:**
Replaced all `sh` commands with `bat` (Windows batch) commands in Jenkinsfile:

```groovy
// Before:
sh 'npm install'

// After:
bat 'npm install'
```

**Outcome:**
All pipeline stages execute successfully on Windows environment.

**Learning:**
Always use platform-specific shell commands (`bat` for Windows, `sh` for Linux/Mac) or use Jenkins' Platform plugin for cross-platform compatibility.

# Additional Features

## Feature 1: GitHub Actions Parallel CI/CD Workflow

### Description

Implemented a comprehensive GitHub Actions workflow as an alternative CI/CD solution, demonstrating knowledge of multiple CI/CD platforms. This workflow provides automated testing, building, and security scanning on every push or pull request to the main branch.

### Rationale

**Why this qualifies as an additional feature:**

1. **Parallel Job Execution**: Unlike Jenkins sequential pipeline, GitHub Actions runs test, build, and security jobs in parallel, significantly reducing total pipeline time
2. **Cloud-Native CI/CD**: Demonstrates understanding of cloud-based CI/CD vs. self-hosted Jenkins
3. **Enhanced Security**: Includes vulnerability scanning (npm audit, Trivy) not present in basic Jenkins pipeline
4. **Cross-Platform Testing**: Runs on GitHub-hosted Ubuntu runners, testing Linux compatibility
5. **Artifact Management**: Automatically uploads coverage reports with 30-day retention

### Implementation

**Workflow Configuration (`.github/workflows/ci-cd.yml`):**

```yaml
name: CI/CD Pipeline - Chess Ranking System

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

env:
  NODE_VERSION: '18'

jobs:
  # Job 1: Comprehensive Testing
  test:
    name: Run Tests
    runs-on: ubuntu-latest

    steps:
    - uses: actions/checkout@v3

    - name: Setup Node.js
      uses: actions/setup-node@v3
      with:
        node-version: ${{ env.NODE_VERSION }}
        cache: 'npm'

    - run: npm ci
    - run: npm run test:unit
    - run: npm run test:api

    - name: Install Playwright browsers
      run: npx playwright install --with-deps

    - run: npm run test:frontend
    - run: npm run test:coverage

    - name: Upload coverage
      uses: actions/upload-artifact@v3
      with:
        name: coverage-report
        path: coverage/
        retention-days: 30

  # Job 2: Docker Build & Test
  build:
    name: Build Docker Image
    runs-on: ubuntu-latest
    needs: test  # Only if tests pass

    steps:
    - uses: actions/checkout@v3

    - name: Set up Docker Buildx
      uses: docker/setup-buildx-action@v2

    - name: Build Docker image
      uses: docker/build-push-action@v4
      with:
        context: .
        push: false
        tags: chess-ranking:${{ github.sha }}
        cache-from: type=gha
        cache-to: type=gha,mode=max

    - name: Test container
      run: |
        docker run -d -p 5000:5000 --name test chess-ranking:${{ github.sha }}
        sleep 5
        curl -f http://localhost:5000 || exit 1

  # Job 3: Security Scanning
  security:
    name: Security Scan
    runs-on: ubuntu-latest

    steps:
    - uses: actions/checkout@v3

    - name: npm audit
      run: npm audit --audit-level=moderate
      continue-on-error: true

    - name: Trivy vulnerability scan
      uses: aquasecurity/trivy-action@master
      with:
        scan-type: 'fs'
        format: 'sarif'
        output: 'trivy-results.sarif'

    - name: Upload scan results
      uses: github/codeql-action/upload-sarif@v2
      with:
        sarif_file: 'trivy-results.sarif'
```

### Technical Features
